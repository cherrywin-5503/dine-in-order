# 代码讲解单（演示时老师可能提问，先读这一份）

## 1. 一句话介绍

顾客用手机扫店内的统一点餐码，选菜付款（模拟支付），拿到取餐号；店员在电脑或手机上接单、出餐、叫号；店长管理菜单、价格和店员账号。

## 2. 程序架构

三层，依赖方向一律向下：

```
手机/电脑浏览器（public/ 三个页面）
        │  HTTP + JSON
        ▼
接口层  src/app.js        路由、登录校验、角色校验、统一返回格式
        ▼
业务层  src/auth.js       登录、token
        src/menu.js       分类、菜品、规格、价格计算
        src/orders.js     订单状态机、取餐号、支付确认、退款、定时任务
        src/mockpay.js    模拟微信支付（以后可以换成真实支付）
        ▼
数据层  src/db.js         SQLite 建表、事务
```

- 前端三个页面分别是顾客端、店员端、店长端，各自一个 JS 文件。
- 前端不信任：金额、价格、权限都由后端重新算、重新判断。

## 3. 技术栈和选择理由

- **Node.js + 自带 http 模块**：不依赖第三方包，装好 Node 就能跑，不会出现“依赖装不上”。
- **SQLite（node:sqlite）**：单店一台电脑，不需要单独装数据库服务，文件即数据库，支持事务和唯一约束，满足设计文档里的幂等和防重复要求。
- **原生 HTML/CSS/JS**：页面不多，不需要框架；手机优先、电脑也能用。
- **轮询（每 2~5 秒）而不是 WebSocket**：单店只有几台设备，轮询简单可靠，断网恢复后自动补上（设计文档 D2）。
- **MockPay**：真实微信支付需要商户号和备案域名，业务层只调用适配器的接口，以后只改 `mockpay.js`。

## 4. 功能和代码的对应（FR 编号同需求文档）

顾客端
- FR-01 扫统一点餐码进入菜单：`public/qr.html` + `src/qr.js` 生成二维码；`public/js/customer.js` 的 `renderMenu`，没有桌号。
- FR-02 分类菜单、售罄置灰：`menu.customerMenu`；`customer.js` 的 `renderMenu`（`soldout` 样式）；下单时 `menu.priceOf` 再校验（返回 40902）。
- FR-03 规格和备注：`customer.js` 的 `openSpec`；`menu.priceOf` 计算规格加价；`orders.checkRemark` 限制 50 字。
- FR-04 购物车：`customer.js` 的 `addToCart`、`renderCheckout`；服务端 `orders.buildLines` 重新算金额。
- FR-05 支付后才交给店员：`orders.onPaid` 把订单从“待支付”改成“待接单”；`orders.staffList` 只列已付款的订单。
- FR-06 15 分钟未支付关闭：`orders.insertPayment` 写过期时间；`orders.closeExpired` 定时关闭；阈值在 `src/config.js`。
- FR-07 取餐号和排队数：`orders.onPaid` 里在 `daily_counter` 计数器加 1 分配取餐号；`orders.queueAhead` 计算“前面还有 N 个订单”；`customer.js` 的 `renderOrder` 显示。
- FR-08 追加菜品：`orders.addOn` 新建一个批次的支付；`orders.onPaid` 的追加分支让新菜生效，订单号和取餐号不变。
- FR-09 没有取消按钮：`app.js` 里没有顾客取消订单的接口；订单页只有提示文字。

店员端
- FR-10 新订单提醒、5 分钟再提醒：`public/js/staff.js` 的 `poll`（每 2 秒）和 `beep`；`orders.remindUnaccepted` 写入提醒时间；`orders.staffList` 计算是否超时标红。
- FR-11 状态依次改变：`orders.changeStatus` 用条件更新（`WHERE status=?`），跳过会返回 40901；状态规则集中在 `orders.TRANSITIONS`。
- FR-12 售罄和恢复：`menu.setSoldOut`；`staff.js` 的 `renderSoldOut`；顾客菜单每 4 秒检查一次。
- FR-13 退款：`orders.refund`（原因必选，记录操作人和时间）；失败后 `orders.retryRefund` 用同一个退款单号重试；`staff.js` 的 `refundDialog`。
- FR-14 店员不能改价：`app.js` 的角色校验，改价接口只允许店长；订单金额只由服务端计算。

店长端
- FR-15 菜品管理：`menu.saveDish`；`public/js/manager.js` 的 `dishForm`。
- FR-16 改价只对新订单生效：订单明细 `order_item.unit_price_fen` 保存下单时的价格快照；`menu.saveDish` 只改菜品表。
- FR-17 店员账号：`app.js` 的 `/api/manager/staff`；`auth.verify` 每次请求都检查账号状态，停用后立即失效。
- FR-18 按日期查订单：`orders.listByDate`；`manager.js` 的 `tabOrders`。

新增功能（需求文档之外）
- 语音叫号：`staff.js` 的 `speak`（浏览器 `speechSynthesis`），在 `changeStatus` 里状态变为已完成时触发。
- 取餐提醒：`customer.js` 的 `notifyDone`（弹窗 + `navigator.vibrate` + 提示音）；订单页每 5 秒、菜单页每 4 秒检查一次状态变化。
- 营业统计：`orders.stats`（SQL 汇总，营业额 = 已支付 − 已退款）；`manager.js` 的 `tabStats`；接口只允许店长。
- 菜品图片上传：`manager.js` 的 `upload`（浏览器缩图）→ `app.js` 的 `/api/manager/upload`（校验类型和大小，保存为文件）→ `/uploads/` 静态访问。

## 5. 几个关键设计，建议会讲

- **订单状态机**：8 种状态，合法转移集中写在 `orders.TRANSITIONS`，其他转移一律拒绝。状态只能往前走。
- **支付结果确认（幂等）**：微信通知、支付后主动查单（A6）、定时对账，三条路谁先到都调用同一个 `onPaid`。它先检查这笔支付是不是已经成功，成功了就直接返回，所以重复通知不会重复分配取餐号。演示：支付窗口里有“通知丢失”的演示选项。
- **条件更新**：`UPDATE ... WHERE id=? AND status=?`。两个店员同时点同一个订单，只有一个能成功，另一个返回 40901。
- **价格快照**：下单时把菜名、规格、单价存进订单明细，之后改价、改名都不影响历史订单。
- **防重复下单**：下单带一个随机的 `request_id`，数据库对 (用户, request_id) 有唯一约束。网络超时重试，返回的是同一个订单。
- **取餐号**：每天从 001 重新开始，在计数器行里加 1（事务内串行），并有 (日期, 取餐号) 的唯一索引兜底。
- **排队数**：同一天、状态是“待接单”或“制作中”、取餐号比本单小的订单数。
- **金额用整数“分”**：避免浮点误差，界面显示时再 ÷100。
- **安全**：每次请求校验登录和角色；顾客只能看自己的订单；密码用 scrypt 加盐哈希保存；SQL 全部参数化；用户输入显示前做了转义，防止注入网页脚本。
- **定时任务只靠扫描数据库状态**：服务重启后继续扫描，不会丢任务。

## 6. 老师可能问的问题（参考回答）

1. **这个功能由哪段代码实现？** 对照上面第 4 节，说出文件和函数名，打开代码给老师看。
2. **为什么没用微信小程序？** 小程序需要 AppID、备案域名和微信商户号，课程周期内办不下来；业务逻辑和接口不变，网页版可以在手机和电脑上现场运行，换成小程序只需要重写前端。
3. **支付是真的吗？** 不是，是 MockPay 模拟。设计文档里就写了开发和演示用 MockPay；真实微信支付只需要替换 `mockpay.js`，业务层不用改。
4. **用户重复点支付按钮会怎样？** 按钮提交后置灰；后端 `onPaid` 幂等，同一笔支付只处理一次。
5. **店员同时点同一个订单会怎样？** 条件更新，只有一个成功。
6. **服务重启后，没付款超时的订单会怎样？** 定时任务靠扫描数据库，重启后继续扫描，照样关闭。
7. **怎么保证店员不能改价？** 改价接口只对店长开放，其他角色返回 40301；订单金额由服务端计算。可以用测试 `NFR-06/FR-14 越权测试` 演示。
8. **数据库为什么选 SQLite？** 单店单机，不需要单独的数据库服务，且支持事务和唯一约束。
9. **怎么测试的？** `npm test` 有 29 个自动化测试，覆盖主流程、异常（通知丢失、超时、金额不符）、越权；另外在手机上手工测了主流程（演示前请自己真的测一遍再这样回答）。
10. **有哪些没做？** 真实微信支付和回调、图片上传、每日备份、HTTPS 部署，见 `docs/与设计文档的差异.md`。
